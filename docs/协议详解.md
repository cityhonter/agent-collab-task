# 协议详解

> 「Agent 任务中转站」核心协议的完整说明。

---

## 一、核心思想

**"一个共享文件，多个 agent 协作"**

```
        ┌─────────────────────────────────┐
        │  中转层（共享文件夹）            │
        │                                  │
        │  当前关注.md     ← 索引         │
        │  code/active/   ← 待执行       │
        │  code/done/     ← 已完成       │
        │  templates/     ← 模板         │
        │  archive/       ← 归档         │
        └─────────────────────────────────┘
                  ↑↓ read/write
     ┌────────────┴────────────┐
     │                         │
  Agent A                  Agent B
 (WorkBuddy)              (Cursor)
 (制定任务)                (执行任务)
```

---

## 二、双角色详解

### 2.1 制定者（Planner）

**职责：** 把用户需求转化为结构化任务，存入中转层。

**典型用户：**
- 人类（最常见）
- 规划型 agent（如 WorkBuddy 主会话）
- 自动化脚本

**输入：** 模糊需求（如"实现登录功能"）

**输出：** 完整的任务文件（frontmatter + 5 段正文）

### 2.2 执行者（Executor）

**职责：** 看到任务、claim、执行、回报。

**典型用户：**
- 各种 AI agent
- 人类开发者
- CI 脚本

**输入：** 索引页 → 选中一个任务

**输出：** 任务文件被修改（status: done，result 已填）

## 三、任务状态机

### 状态图

```
                    ┌─────────────────────────────────┐
                    │                                 │
                    ↓                                 │
  ┌─────────┐  claim  ┌─────────┐   done   ┌─────────┐
  │ pending ├────────>│ claimed ├─────────>│  done   │
  └─────────┘         └────┬────┘          └────┬────┘
       ↑                   │                    │
       │                   │ 超时（24h）         │ 归档
       │                   │ 无更新              ↓
       │                   ↓                ┌─────────┐
       │              ┌─────────┐           │archived │
       │              │ 回到    │           └─────────┘
       │              │ pending │               ↑
       │              └─────────┘               │
       │                                        │
       │  ┌──────────┐                           │
       └──┤cancelled │<──── 用户取消 ─────────────┤
          └──────────┘                           │
```

### 状态字段

| 状态 | 含义 | 谁能改 |
|------|------|--------|
| `pending` | 待领取 | 任何 agent |
| `claimed` | 已认领（被某 agent 持有）| 该 agent |
| `done` | 已完成 | 执行者 |
| `blocked` | 被卡点阻塞 | 制定者标记 / 执行者报告 |
| `cancelled` | 用户取消 | 制定者 |
| `archived` | 归档（从 active 移到 archive）| 任何人（建议周日批量） |

### 状态转换规则

1. **pending → claimed**：任何 agent 读 `claimed_by` 为空时 claim
2. **claimed → done**：执行者完成所有完成标准
3. **claimed → pending**（超时）：`claimed_at` 超过 `CLAIM_TIMEOUT_HOURS` 无更新，任何人可重新 claim
4. **任何状态 → cancelled**：用户明确取消
5. **done → archived**：周日/定期归档（一般人工操作）

## 四、锁规则（核心防撞机制）

### 4.1 为什么要锁？

多 agent 协作最大的风险是**重复执行**。A agent claim 一个任务开始干，B agent 不知道也在干同样的事。锁机制确保**一次只有一个 agent 在做事**。

### 4.2 锁的实现

锁是**软锁**（不是 OS 锁文件），靠任务文件的 frontmatter 实现：

```yaml
claimed_by: "codeBuddy-阿宝"
claimed_at: "2026-08-20T15:30:00"
```

### 4.3 claim 前必查

执行者在 claim 任务**之前**，必须：

1. `Read` 任务文件
2. 检查 `claimed_by` 字段：
   - **空字符串** → 可以 claim
   - **非空且 `claimed_at` 在 `CLAIM_TIMEOUT_HOURS` 小时内** → **不许碰**
   - **非空但超时** → 可接管（但要写明"我是接管者"，建议在 `result` 字段标注）
3. **先写锁，再做**（避免被其他 agent 抢）

### 4.4 锁检查代码示例（伪代码）

```python
def claim(task_file):
    task = read_frontmatter(task_file)
    if task.claimed_by and not is_timeout(task.claimed_at, CLAIM_TIMEOUT_HOURS):
        return False, f"已被 {task.claimed_by} 领取，等待 {CLAIM_TIMEOUT_HOURS}h 超时"
    
    # 先上锁
    task.status = "claimed"
    task.claimed_by = AGENT_ID
    task.claimed_at = now_iso()
    write_frontmatter(task_file, task)
    
    return True, "claim 成功"
```

### 4.5 超时接管

如果一个 agent claim 后**超过 `CLAIM_TIMEOUT_HOURS` 小时**没更新（比如崩溃、断网、被用户关闭）：

- 任何其他 agent 可以 claim
- 但建议在任务文件加一行注释：

```markdown
> 接管说明：原 claim agent {old_claimed_by} 于 {time} 超时未更新，由 {new_agent} 接管
```

## 五、任务文件结构详解

### 5.1 完整 frontmatter

```yaml
---
type: code                    # code / other
status: pending               # 状态
claimed_by: ""                # 认领者
claimed_at: ""                # 认领时间
result: ""                    # 完成结果
project: 项目名                 # code 任务必填
category: 学习/求职/...         # other 任务必填
priority: P1                  # P0/P1/P2/P3
created: 2026-08-20           # 创建日期
updated: 2026-08-20           # 最后更新
agent_hint: "提示信息"         # 给执行者的提示
---
```

### 5.2 正文结构（5 段式）

任何任务文件正文都应包含以下 5 段，顺序可调但必备：

1. **目标** — 一句话说清要达成什么
2. **背景/上下文** — 为什么做、关联项目、客户背景
3. **输入/前置** — 代码路径、文档、参考资料
4. **输出/交付物** — 新增/修改的文件、自测方法
5. **完成标准** — ≤3 条可验证的勾选条件

可选段：
- **不要做** — 明确边界，避免越界
- **卡点** — blocked_by 标记

### 5.3 完成标准设计原则

✅ **好的完成标准：**
- "新增 `D:\item-product\xxx\Dockerfile` 文件"
- "`docker compose up -d` 后 `curl http://localhost` 返回 200"
- "git push 后 GitHub 仓库能看到 4 个新文件"

❌ **不好的完成标准：**
- "写完代码"（无法验证）
- "差不多就行"（主观）
- "完成度高"（无法量化）

## 六、索引页（`当前关注.md`）规则

### 6.1 作用

一页看清所有任务状态。agent 入口。

### 6.2 规则

- **只放指针**，不放任务详情
- 任何状态变化都同步更新
- 至少包含 frontmatter：`updated`、`total_active`
- 表格分两类：code / other

### 6.3 状态图例

| 图例 | 状态 | 含义 |
|------|------|------|
| 🟡 | pending | 待领取 |
| 🔵 | claimed | 已被认领（带 AGENT_ID）|
| 🚫 | blocked | 被卡点阻塞 |
| ✅ | done | 已完成（本周）|
| 📦 | archived | 已归档 |

## 七、异常处理

### 7.1 TRANSIT_ROOT 不存在

agent 应自动：

```bash
mkdir -p <TRANSIT_ROOT>/{code,other}/{active,done}
mkdir -p <TRANSIT_ROOT>/{templates,archive}
cp templates/当前关注.md.template <TRANSIT_ROOT>/当前关注.md
```

### 7.2 同名任务已存在

agent 应**询问用户**："已存在同名任务，是更新它还是新建？"

### 7.3 任务被多个 agent 抢

理论上不会发生（锁机制），但如果发生：

- 后 claim 的 agent 主动放弃
- 在任务文件追加"冲突说明"段落

### 7.4 配置文件丢失

agent 重新走 AskUserQuestion 流程。

## 八、最佳实践

### 8.1 任务粒度

✅ **合适粒度：** "实现登录页面" / "修复订单查询超时 bug" / "部署前端到生产"

❌ **太粗：** "做完整项目"

❌ **太细：** "在 Login.vue 第 23 行加 v-if 判空"

经验：**一个任务 = 一个 agent 一次会话能完成的工作量**

### 8.2 完成标准数量

3-5 条最好：
- 太少（1 条）→ 粒度太粗
- 太多（>5 条）→ 应拆成多个任务

### 8.3 优先级

| 优先级 | 含义 |
|--------|------|
| **P0** | 阻塞其他任务、必须立即做 |
| **P1** | 本周计划 |
| **P2** | 本月计划 |
| **P3** | 想到再说不急 |

### 8.4 卡点（blocked_by）

如果任务被某个东西阻塞：

```yaml
blocked_by: "等张总回复需求确认（2026-08-22）"
```

agent 看到这个会**主动报告**，不强行继续。
